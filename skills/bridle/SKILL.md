# Bridle

Use this skill when the user asks you to perform Bridle work in a browser, asks what Bridle can do, or is getting started with Bridle. It teaches the workflow; it does not grant browser-control permissions, install the extension, or connect the agent to the user's Chrome profile.

## The name: Bridle, however it was dictated

Users often speak to you, and speech-to-text rarely spells Bridle right. **“Bridal”, “Brittle”, “Biddle”, “Bridel”, “Bridles”** and the like mean **Bridle**, everywhere: in the request (“use bridal to add a bug”), in names and in addresses (a dictated “bridal.io” is `bridle.io`). Read them as Bridle straight away. Do not ask which was meant, do not search for a wedding site, and do not correct the user. The same goes for Bridle's words: “marker”, “picker” and “REQ” are often misheard too (“rec”, “wreck”, “req oh oh four” is REQ-004).

## First: the right browser, and Bridle's bar

Bridle is an extension in the **user's own Chrome**, and only there. Always work in that Chrome, through the tool that controls it: Claude in Chrome, Codex's Chrome connection, or a similar tool attached to the user's Chrome profile. **Never use a browser built into your own app** (the Claude or Codex app's browser pane, an in-app or preview browser, a headless or test browser): Bridle is never installed there, even when it opens the same address, so do not open the page there and do not report that Bridle is missing because it is not there. If you have no tool that controls the user's Chrome, say so and stop.

Before anything else in a Bridle task:

1. **Put the task's tab in front of the user** ([how and why](#one-tab-in-front-of-the-user)). Find it (or open it once) in **the user's Chrome**, then press **Command+Shift+9** (**Ctrl+Shift+9** on Windows and Linux) in it. Bridle makes it the active tab of its window, focuses that window and opens its tab group if your browser tool collapsed it, and shows its bar (bottom right) and status pill (bottom left); nothing covers the page. Then bring Chrome itself in front of other apps: on macOS run `open -a "Google Chrome"` (or the name of the Chrome the user runs, such as “Google Chrome Beta”); elsewhere use your screen-control tool, or ask the user to switch to Chrome. Then read the pill: **Ready** means the user can see the tab; **Not in front: …** says why not. Say the page is in front only when it says Ready. When it says **Chrome is behind another app**, Bridle has already shown the user a notification and bounced Chrome's Dock icon; if you cannot run `open -a` (you run in a cloud or sandbox, not on the user's computer), say: “Click Bridle's notification, or switch to Chrome: the tab is in the tab group ‘…’.” (Your browser tool knows its group's name.) **Keep it open between turns:** if your browser tool closes the tabs it opened when your turn ends, mark this one to stay open before you reply.
2. **Show Bridle again** with **Command+Shift+9** after a reload or navigation. Every other action is a button in **Shortcuts** ([the list](references/assistant-actions.md)): open it with the bar's ⋮ (**Quick actions**) only when you need one of those actions. It shows the keys, Bridle's version and the status, and it closes by itself (after a minute, at a press outside it, when an action runs): the user is watching the page, so never keep it open.
3. **Read the status after every action.** A dark pill at the bottom left, **Bridle · …** (also a status in the page for tools that read it), says what Bridle is doing: **Ready**, **Not in front: …** (the user cannot see this tab: [bring it forward](#one-tab-in-front-of-the-user)), **Getting ready to pick: do not click yet**, **Choose what the feedback is about**, **Writing feedback on** “…” (the note is open; the note's own element line names the HTML element), **Saving…**, **Saved REQ-… · Type**, **Updated REQ-… · Type** (after an edit), what a panel action opened (**Quick Notes open**, **Feedbacks list open**, **Copied the AI prompt…**), **Waiting for the person: …** (a confirmation or picker that is theirs), or why it stopped (**Not saved**, **Stopped**, **… did not open**). It shows for a few seconds after each change and then fades; its words stay readable to your page reader (a status named **Bridle …**), so read it right after each action. A screenshot without the pill means it faded, not that nothing happened. Act on what it says. Never press a shortcut or button again “to make sure”: that is how drafts get cancelled and feedback saved twice. Start again only when it still says **Ready** after you started something (nothing happened).
4. **Press only what is named:** a button in Shortcuts, or a control a step here names. Never explore. The round pencil above the bar is **Quick Notes** (the person's notepad, not feedback). Bridle's icon in Chrome's toolbar and the settings it opens are the user's: never press them. If what you expect is not there, read the status and tell the user exactly what it says.
5. **Every new feedback:** press **Command+Shift+8** (**Ctrl+Shift+8**). Click the element **only once the status says Choose what the feedback is about**: before that, Bridle is still getting the picker ready and swallows clicks, and without the picker a click is a click on the page (it follows a link, presses a button). If a click you meant as a pick changed the page, go back and tell the user. The note opens beside it (status: **Writing feedback on** “…”): check the note's element line, set the type, write, press **Save**, and the status says **Saved REQ-…**. While a feedback is being added, Bridle's own badges and notes step aside, so what you see is the page itself. Pressing Command+Shift+8 again while picking or while a note is open does nothing. Details: [visual feedback](references/visual-feedback.md#capturing-feedback-as-an-assistant). **Changing a saved feedback** is an edit, never a new one: press its badge (**REQ-… feedback badge: …**), then **Edit REQ-… feedback**, change the words and press **Update**; the status says **Updated REQ-…**. No badge on screen: [edit an existing item](references/visual-feedback.md#edit-an-existing-item).
6. **A shortcut did nothing?** Go down this list, one step at a time, and stop at the first that works:
   1. Click an empty part of the page (not a link or a field), so the page has the keyboard, and press the shortcut once more.
   2. For a feedback: open **Shortcuts** (the bar's ⋮) and press **Add feedback** there. Shortcuts also says when a shortcut is not set (another extension may own the key); tell the user it can be set in `chrome://extensions/shortcuts`.
   3. **No status pill at all**, even after the shortcut with the other modifier ([the keys](#the-keys-are-those-of-the-users-computer)), and the bar's ⋮ opens a short menu with no **Add feedback**: this Bridle is older than this skill. Start each feedback by holding **Command+Shift** (**Ctrl+Shift**) while clicking **Pick any element to add feedback** on the bar, and tell the user that updating Bridle makes this easier. No bar at all: you may be in the wrong browser, or Bridle is missing, turned off or not allowed on this site; check which (see [visual feedback](references/visual-feedback.md)) and tell the user the specific reason. **“Bridle is not active”**, or a bar whose count shows ↻ (“Reload this page to reconnect Bridle”), means Bridle was updated or reloaded since the tab opened: its bar there no longer works. Tell the user, and reload the tab only with their OK (the page may hold unsaved work), then press the shortcut again.

## One tab, in front of the user

A Bridle task happens in **one tab of the user's Chrome, and that tab is in front**: the user watches what you do there, and Bridle needs it too (Chrome lets Bridle take a screenshot only of the tab showing in its window). Working in a tab the user cannot see is a failure, even when every step succeeds.

1. **Find the tab before opening anything.** List the tabs of every window of the user's Chrome. Some browser tools (Claude in Chrome) see and act only on the tabs of their own tab group, often in a window of their own: with such a tool you cannot list or use the user's other tabs. Say so plainly, never say you used the tab the user had open, and offer the two ways that work: open the page in your own group, or ask the user to drag their tab into your group (it has your group's name in Chrome's tab strip); then press Command+Shift+9 in it. A tool that can use any tab of the user's Chrome (Codex's) keeps doing so: take the user's own tab as below.
   - **No address** (“this page”, “the site I have open”, “what I'm looking at”): the tab that is showing, the active tab of the window the user last used. With several windows (often one per screen), each shows its active tab: take the one whose site fits what the user said, and if more than one could be it, name them and ask once.
   - **An address or a site name** (“open bbc.co.uk”): a tab already on that site is the one. Prefer one that is showing in a window, then the one used most recently, and the same page over another page of the site. Switch to it; change its address only when the user asked for a different page.
   - **Not open anywhere:** open it once, as a new tab in the window the user is looking at, not in a window of your own.
2. **Bring it to the front, every time, in two steps.**
   - **Inside Chrome:** press **Command+Shift+9** (**Ctrl+Shift+9**) in the tab. Bridle makes it the active tab of its window, focuses that window, and opens its tab group when your browser tool put it in a collapsed group of its own. The tab stays in that group, so your tool keeps working in it: do not move it out. (With an older Bridle that does not do this, make it the active tab and focus its window with your browser tool.)
   - **Chrome in front of other apps:** the user is often talking to you in another app (the Codex or Claude app) that covers Chrome, and a browser tool's “select tab” or “focus window” changes nothing about that: every step succeeds and the user still sees your app. On macOS run `open -a "Google Chrome"` (use the name of the Chrome the user runs, such as “Google Chrome Beta”); it needs no permission and raises Chrome's front window, which is why the tab's window is focused first. Elsewhere, use your screen-control tool, or ask the user to switch to Chrome.

   Do both when you start, whenever the user asks to see it, and whenever you come back after something else took the front (another app, a download, a dialog, a tab you opened to check something).
3. **Check, then say it.** Right after, read Bridle's status pill. **Ready** means this is the tab showing in its window and Chrome is the app in front; only then say the page is in front. **Not in front: another tab is showing** or **Not in front: Chrome is behind another app** means the user cannot see it. Do both steps again once. If it still says Not in front, tell the user exactly where the tab is (“It's in Chrome, in the tab group ‘…’”) and ask them to click it; never open the page again. **Chrome behind another app** is the one Bridle cannot fix itself (macOS does not let an extension bring Chrome in front of the app the user is in): it shows the user a notification, “Your AI assistant is working in Chrome: click to see it”, and bounces Chrome's Dock icon, and the pill says so. Clicking it brings the tab forward. When you cannot run `open -a` (a cloud or sandboxed assistant), that notification is the way: tell the user to click it, or to switch to Chrome. (With an older Bridle that shows no such status, run `document.hasFocus()` in the page: `true` means in front; `document.visibilityState` is not enough, it stays `"visible"` while another app covers Chrome. If it is `false`, or you cannot run it, ask “Can you see it?”.) When the user says they cannot see it, it is not in front: do both steps again; do not open the page again. (Later, when the user clicks back into your app to talk, `hasFocus()` turns `false` although Chrome may still be in view, on another screen or beside your app: check right after bringing it forward, not before every step.)
4. **Keep it open between turns.** A Bridle task goes on after your reply: the user says what to capture next, or is typing in Bridle's note when you speak again. The tab must still be there. Some browser tools close the tabs they opened when your turn ends (Codex's does, unless a tab is marked to stay open): mark the task's tab to stay open as soon as you open or adopt it, before you reply. Never close the task's tab yourself: it is the user's, whether you found it or opened it, and closing it mid-task loses a draft that is not saved yet.
5. **Stay on that tab.** Remember it (its tab id and address) for the whole task: every capture, Copy prompt, check and Bridle action happens there. When the user asks you to “open” the same site again, switch to that tab; never open a second copy. A reload, or a link followed inside it, keeps it the same tab. Open another tab only for a different page the user asks for, or for a local or test copy when you verify a fix: say which tab you are in, and come back to the Bridle tab afterwards.
6. **Follow the user's own moves.** If the user has gone to another tab themselves and says “here” or “this page”, the tab now showing becomes the task's tab.

## The keys are those of the user's computer

Bridle's shortcuts are **Command+Shift+9** (show Bridle, assistant mode on) and **Command+Shift+8** (start a feedback) when the user's Chrome runs on a Mac, and **Ctrl+Shift+9** / **Ctrl+Shift+8** on Windows, Linux and ChromeOS. What counts is the computer Chrome runs on, not yours: an assistant in a cloud sandbox runs on Linux while the user's Chrome is often on a Mac. When you are not sure, check in the page first (`navigator.platform` contains “Mac”). (Bridle on a Mac also accepts Ctrl, for assistants that guessed wrong.)

**Assistant mode comes on only through these keys.** Press Command+Shift+9 before anything else and read the status pill: no pill means the key did not count, so press it again with the other modifier (Ctrl instead of Command, or the other way round) before you think of an older Bridle. Start every feedback with Command+Shift+8, never with a plain click on the bar's picker: a plain click is the person taking over (the full form opens and assistant mode goes off). And never click a page element to add feedback until the status says **Choose what the feedback is about**: without the picker, a click acts on the page (a link is followed).

## When you run in a cloud sandbox

Some assistants run their commands in a cloud sandbox, not on the user's computer (the Claude app's chat, cloud tasks): your shell shows a Linux system, often `/root`, while the user's Chrome is on their own computer. Your browser tool's clicks and key presses still reach that Chrome, so Bridle works. What changes:

- **Keys:** the user's computer's keys (above), not your system's.
- **Chrome in front:** you cannot run `open -a`. When the pill says **Chrome is behind another app**, Bridle has shown the user a notification: tell them to click it, or to switch to Chrome.
- **Prompts:** Bridle's AI folder is on the user's computer, so you cannot read it: use **Full prompt**, never Short.
- **This skill** lives in your sandbox for this chat only. Tell the user once how to keep it: in the Claude app, Settings → Capabilities → Skills, upload `bridle.zip` (it is then in every new chat, with no download); in other apps, their own skill settings.
- **Code changes** need the website's repository on the user's computer: for capture-then-fix, suggest Claude Code or Codex there.

## Installed during this conversation

If the Bridle skill was installed earlier in this same conversation, your assistant may not have loaded it for this chat. Read the installed `SKILL.md` (and the reference a step needs) before acting on a Bridle request here, and tell the user that new chats load it by themselves.

## First-time setup and discovery

On the first Bridle-related interaction, unless the user has already confirmed setup or supplied a Bridle **Copy AI prompt**, begin with a short getting-started guide and ask them to complete setup at [bridle.io/setup](https://bridle.io/setup). Do this by default when they ask what Bridle can do, ask how to start, or install the skill. Include the guide and next action in the initial response; do not wait for a separate setup question or stop at a vague prerequisite such as “install the extension” or “enable browser access.” Do not provide the Chrome Web Store URL unless the user explicitly asks for the direct store link.

1. Open the [Bridle setup guide](https://bridle.io/setup) and follow its install steps. Pin or open Bridle in the Chrome profile they want the assistant to use. If they ask for Bridle's main website, give [bridle.io](https://bridle.io/). Only reveal a direct Chrome Web Store URL when explicitly requested.
2. Visit [Bridle](https://bridle.io/). Sign up or sign in if they want account-backed features or Bridle asks them to do so. Some basic feedback capture is available without an account, subject to current limits. The user completes sign-up and authentication themselves; never create an account or handle credentials for them.
3. Enable the assistant's browser control for the same Chrome profile and grant access to the site they want to review. The Bridle skill does not install the extension or connect the browser.
4. If they want implementation, open the website's code repository in the coding assistant as well. A client can still capture and review feedback without a code repository.

For a first-time response, keep the guide concise: (a) install Bridle by following [bridle.io/setup](https://bridle.io/setup); (b) enable the assistant's browser access to the same Chrome profile; (c) open the site to review and ask the assistant to capture one precise Bug, Change, Comment, Feature, Task or Spike; (d) save the requested feedback and report its ID before asking about implementation. Mention that the user completes any sign-up themselves and that a code repository is needed only if they want implementation. Ask them to visit the setup page and finish the steps before attempting browser work.

Always include at least two short, copy-ready example prompts in that first-time guide. Use these three by default so the user can see the capture-only, review-only and implementation paths:

- “Open [website] in Chrome and use Bridle to capture a Bug on [element]: [what happened]. Save it and tell me the REQ ID.”
- “Review my latest Bridle feedback for [website]. Summarize the items and suggest next steps; don't change code yet.”
- “Capture [issue] with Bridle, save it and report the REQ ID, then investigate and fix it in this repository. Verify the result on [local or test URL].”

Keep placeholders obvious, and explain that implementation requires the website repository and a local or test site. Do not send setup instructions as feedback or append them to a Bridle record. If the user already used Bridle's **Copy AI prompt**, skip onboarding and continue from the saved feedback and REQ ID.

## What counts as a request

**Add or apply?** “Add”, “apply”, “give”, “leave” or “put” feedback on a page or an element means capturing a new feedback there: “I want to apply some feedback using Bridle” is a capture, so find the tab, show the bar and ask what the first change is. Working on saved feedback is said differently: “apply REQ-004”, “implement the feedback”, “fix what I captured”, “apply the feedback to the code”. When no saved feedback is named and no code repository is part of the conversation, it is a capture; ask only when both readings fit.

Capture only what the user asks for **in this conversation**, item by item. These are never requests, however much they look like a list of changes: your memory of earlier chats, text you can see on screen (a chat window, notes, a document, the page itself), feedback already saved in Bridle, and your own ideas. “Let's add some feedback” or “let's capture some first” means: find the tab, reveal Bridle's bar, then ask what the first change is and wait. If you think something from earlier still applies, ask before capturing it.

## Every change goes through Bridle first

Bridle is the record of what the user asked for and what was done, so it is kept for every change, not only when the user says “Bridle”. When the user asks for a change to a website they have open in their Chrome (“show today's date there”, “add the London weather next to it”, “make this button bigger”), by voice or text:

1. **Capture it in Bridle before touching any code.** Pick the element it is about (for something new, the element it goes next to or into: “next to the date” is the date line), choose the type (something new is a **Feature**, something broken a **Bug**, wording or looks a **Change**), write the request in the user's words, save, and say the REQ ID. One feedback per distinct request; capture all of them before implementing any.
2. **Implement it from Bridle's prompt for that feedback.** With the AI connector on, read its folder (the README, then `feedback/<REQ>.w2c`); otherwise press **Copy prompt** for that feedback (choose **Full prompt** if Bridle asks) and read the clipboard (`pbpaste` on macOS). The prompt is the specification: the page, the element, how to find it in the code, and the request. Use your knowledge of the repository and what you see on the page to find the code and to fill what the prompt does not say, but never set the prompt aside; if it and what you see disagree, say so and follow the user's words.
   - **Several feedbacks in one prompt:** in Shortcuts press **Copy AI prompt for this page's open feedback** (every open feedback of this page, in one step). To choose them yourself: press **Bridle.io** on the bar to open the Feedbacks list, tick the ones to hand over (each row's checkbox is named **Select REQ-…**), press **Next**, then **Copy prompt for AI tools** (→ **Short prompt** when you can read the connector folder, otherwise **Full prompt**).
   - **You are the AI tool:** copy the prompt and read it from the clipboard yourself (`pbpaste` on macOS, `Get-Clipboard` on Windows, `wl-paste` or `xclip -o -selection clipboard` on Linux). Never use Bridle's buttons that open the Claude, Codex or another app, or a web chat: they hand the prompt to the user's own app. The prompt names every REQ ID and how to report them.
3. **Verify on the page** (reload without the cache), in the task's tab or, for a local or test copy, in a tab you name, with it in front, and report per REQ ID. Check that the result really works as asked: live data comes from where it should (an API call, not a value copied into the code), today's date is today's. End with the completion link from the prompt. When the user asked you to implement the feedback and you control their Chrome, you may open that link yourself; then stop. The green markers, the notes and “Are you happy with the change?” are the user's review: never hide them, delete anything or answer that question unless the user asks.
4. A copied Bridle prompt or a connector item is already saved feedback: reuse its REQ ID; never capture it twice.
5. Other problems you notice on the way are not the user's request: list them; capture or fix one only when asked.
6. If capture is blocked (no access to the user's Chrome, no bar, a quota or sign-in gate), say exactly what blocked it and ask whether to change the code without a Bridle record. Never change the code without one silently.
7. Only the user's own words skip capture (“just change the code, no feedback”). Work that is not a change to a page they are looking at (a refactor, tests, a build script) is not captured.

For reading, review, editing, exports, diagnostics, tickets and completion, use the relevant supported Bridle feature. Repository tools remain necessary for implementation and checks. Do not invent Bridle features or call internal extension messages as a substitute for its visible UI.

## Core operating loop

1. **Understand the request:** the site, the element, the operation (add, edit, review, replay, diagnostics, ticket), and the outcome. A change to a page goes through [Bridle first](#every-change-goes-through-bridle-first). Keep “add a new feedback” apart from “edit the saved feedback”. A wake phrase such as “Hey Codex” is the host's voice mode, not a Bridle command.
2. **Tab, bar, status:** the task's tab in front ([one tab](#one-tab-in-front-of-the-user)), Bridle's bar shown, the status read. Check again before each step; do not rely on remembered screen positions.
3. **Act through what is named:** Command+Shift+8 for a feedback, a Shortcuts button for anything else, then the controls a reference names. When the element line and the text match the request, save at once: the user's request is the permission, so do not read a draft back for approval. Ask first only when the target, type or outcome is genuinely unclear, or Bridle shows an account or quota gate. Never invent a defect, severity or acceptance criteria.
4. **Verify by the status or the result:** Saved REQ-…, the replay playing, the ticket key, the page changed. A click alone is not proof. If it is unclear, look at what is saved before trying again, so nothing is done twice.
5. **Report once** ([rule 17](#rules-learned-from-live-use)). Do not say a ticket exists until its key is shown. Tickets, shared captures and deleting only when the user asked for that operation.

## Rules learned from live use

These come from real sessions in which an assistant drove Bridle in the user's Chrome. Each prevents a failure that happened or nearly happened.

1. **Do not use the right-click menu.** Chrome's native context menu (with **Ask Bridle AI**) is outside the page: browser tools cannot see or click it. Use **Command+Shift+8** (or **Add feedback** in Shortcuts) instead.
2. **Check the target before you save, and correct it in the note.** The line under the text names the element the feedback is on (for example `<h2#title>` “Welcome back”), and the page highlight shows it. If it is something smaller than what the user meant (part of an icon or a drawing, a word inside a link, an inner `span`), press **↑ Parent** until it names the right element; **↓ Back** undoes a step too far. If it is something else altogether, press **Repick** and pick nearer the middle of the element. A wrong pick also shows as text that is not visible on the page (a screen-reader label such as “Homepage” on a logo) or text that does not match what the user named. Never save against a target you doubt; after two failed attempts, tell the user what the line says and ask.
3. **Gates are the user's step.** If Bridle shows **Sign up to continue**, **Subscribe to continue** or **Share limit reached**, stop. Do not press the account, plan or payment button, and do not sign in. Tell the user the gate, keep their request so it can be repeated, and continue only after they say it is handled. **Maybe later** or × only closes the dialog; the feedback was not saved. Anonymous installs can save only a few feedbacks a day, so a batch may stop part-way: report which items were saved.
4. **Keep the user's words and save without a second approval.** If the user says “just say X”, save exactly X. Otherwise turn clear shorthand into a concise request from what was said and what is on screen (“call this Profile” on the label “For you” → “Change ‘For you’ to ‘Profile’”). Do not read back the draft or ask whether to save; save it and report what Bridle confirmed. Ask a brief question only when the target or requested outcome is materially ambiguous. Never invent replacement text, cause, severity or acceptance criteria.
5. **Choose the type on purpose.** The dialog defaults to **Change**. Pick **Bug**, **Comment**, **Feature**, **Task** or **Spike** when the words say so, and report which type you used. Use Comment for questions, observations and general feedback; do not infer a code-change request from a Comment alone. Notes take their type's colour from the type row; Change and Bug are both red. Completed notes are green.
6. **Names from dictation.** Dictation mishears names; Bridle's own name is covered [above](#the-name-bridle-however-it-was-dictated). When a dictated name or phrase is meant to match text on the page and does not (for example a misspelt person's name in a headline), use the page's text and say so. A word that is not on the page at all may be initials or a sound-alike of what is there (“VMO” for “View more”): find the closest text in the part of the page the user named and ask once, naming it.
   - **Spoken addresses.** “forward slash” is `/`, “hyphen” or “dash” is `-`, “dot” is `.`; a trailing “website”, “page” or “site” usually describes the address, it is not part of it (“example dot com forward slash pricing hyphen plans page” is `example.com/pricing-plans`). If the address you built does not exist, find the page before asking: look at the site's navigation or its `/sitemap.xml` for the closest match, then open it or offer the one or two candidates you found. Ask for the address only when nothing on the site matches.
7. **Read the receipt in the status.** After **Save** the status says **Saved REQ-… · Type**; read it at once, because the pill fades after a few seconds (your page reader still finds the words). Report the ID, type and text. Never guess an ID or save twice; with an older Bridle that has no status, find the feedback in the Feedbacks list before trying again.
8. **IDs are per install, across all sites.** “The latest feedback” means the newest on the page or site the user means, not the highest number overall.
9. **Show Bridle first.** Always press Command+Shift+9 before looking for anything of Bridle's. If nothing appears, follow the recovery sequence in the visual reference (shortcut assignment, profile and site access, restricted pages) and report the specific blocker, not only “bar not found”.
10. **Destructive actions need the user's own words.** Delete, remove, reset and turn-off actions only when the user named that action for those items. Deleting a feedback is permanent (there is no recently-deleted list), so stop at the delete confirmation and let the user press it; hiding a marker is reversible and you may do it on request.
11. **Screenshots need the tab in front.** Chrome lets Bridle capture only the visible tab of a window, one more reason to keep the task's tab in front ([one tab](#one-tab-in-front-of-the-user)). If the tab you work in is behind another tab, the receipt reads **Feedback saved · screenshot pending**: Bridle takes the screenshot when that tab is shown with the element on screen. Tell the user when this happens. A PDF exported meanwhile says “Screenshot unavailable”.
12. **Check a fix on a fresh page.** After changing a site's files, reload without the cache before judging the result; a normal reload can show the old page.
13. **Leave Bridle's own questions to the user.** “How did that go?”, the AI connector's question (whether Bridle may keep a folder for AI tools) and “Debugging something tricky?” ask about the user's experience or store a preference; do not answer them. If one covers what you need, say so.
14. **Close only side tabs.** The task's tab ([one tab](#one-tab-in-front-of-the-user)) is the user's: it stays open across turns and after the work, whether you found it or opened it, until the user closes it. Close only tabs you opened for a side job (another page you checked, a local or test copy), and only when the user's whole request is done.
15. **Several matches: count them, ask once.** When the user names something plural (“the install buttons”, “these links”), or more than one element on the page fits the description, find all of them first. Say how many there are and where (“three install buttons: in the hero, in the install card, at the bottom”), then ask one question: one feedback on each (separate REQ IDs), or one feedback covering all of them (multi-element, see [visual feedback](references/visual-feedback.md#one-feedback-on-several-elements)). If the user already said which, do it without asking. Never pick one of several silently.
16. **There is no page-level feedback.** Every Bridle feedback is attached to an element. For “feedback on the whole page” or “not on any particular element”, attach it to the page's main heading (the `<main>` region when there is no clear heading), begin the text with “Across this page:”, and tell the user which element it is attached to. Do not call it page-level.
17. **Report once.** After saving, give each feedback one line: REQ ID, type, its element in a few words, and the text Bridle confirmed. Do not repeat the same result as a separate “complete” summary.

## Bridle's notes on the page

In assistant mode Bridle shows saved feedback as handwritten notes, which can cover parts of the page (several feedbacks on one element are notes one after another, with one arrow). The picker hides them while you choose an element, so they never stop a pick. When you or the user need to see what is under them, press **Show or hide feedback notes** in Shortcuts, say so, and turn them back on when you are done if the user was using them.

## Preferred voice interaction

Interpret requests such as “Ask Bridle to open this page, find the hero heading, and add a change request to rename it…” as: navigate/verify the requested site; use Bridle's element picker; verify the exact heading; write the requested change as an explicit command; save it immediately and report the receipt. Do not pause for approval after drafting. Ask one concise question only when page, target, operation, destination, or requested outcome is materially ambiguous (several matching elements is the usual case: rule 15).

Spoken requests contain fillers, restarts and corrections (“uh”, “no, actually don't do that”, “I want, I want to add…”). Act on the last thing the user settled on, and keep their wording for the feedback text only where they said “say exactly…”.

The Bridle UI and its internal extension message names can change. Use the visible labels and current state first; consult implementation-specific notes in the references only as guidance. Do not call undocumented internal extension messages as if they were a supported third-party API.
