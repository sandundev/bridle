# Bridle

Use this skill when the user asks you to perform Bridle work in a browser, asks what Bridle can do, or is getting started with Bridle. It teaches the workflow; it does not grant browser-control permissions, install the extension, or connect the agent to the user's Chrome profile.

## The name: Bridle, however it was dictated

Users often speak to you, and speech-to-text rarely spells Bridle right. **“Bridal”, “Brittle”, “Biddle”, “Bridel”, “Bridles”** and the like mean **Bridle**, everywhere: in the request (“use bridal to add a bug”), in names and in addresses (a dictated “bridal.io” is `bridle.io`). Read them as Bridle straight away. Do not ask which was meant, do not search for a wedding site, and do not correct the user. The same goes for Bridle's words: “marker”, “picker” and “REQ” are often misheard too (“rec”, “wreck”, “req oh oh four” is REQ-004).

## First: the right browser, and Bridle's bar

Bridle is an extension in the **user's own Chrome**, and only there. Always work in that Chrome, through the tool that controls it: Claude in Chrome, Codex's Chrome connection, or a similar tool attached to the user's Chrome profile. **Never use a browser built into your own app** (the Claude or Codex app's browser pane, an in-app or preview browser, a headless or test browser): Bridle is never installed there, even when it opens the same address, so do not open the page there and do not report that Bridle is missing because it is not there. If you have no tool that controls the user's Chrome, say so and stop.

**The page is often already open.** Users usually say something like “I want to add some feedback on the website I'm working on; I have it open in the browser.” Then list the tabs of the user's Chrome, pick the one with the site they mean (the one they named, or the one they were just using), and work in that tab; do not open a new one. If more than one tab could be it, name them and ask once. Open a new tab only when the user gives an address that is not open yet.

Before anything else in a Bridle task:

1. Focus the user's tab with the page (or open the address they gave) **in their Chrome**.
2. Press the reveal shortcut (**Command+Shift+9** on macOS, **Ctrl+Shift+9** elsewhere). Do it at the start of every Bridle task and again after a reload or navigation.
3. Bridle's bar is now on the page, at the bottom right: a toolbar named **Bridle.io** whose first button is **Pick any element to add feedback**. Find it the way you find anything on a page; after the shortcut, Bridle's bar, notes and receipts are readable and pressable like the page's own elements. No bar: you may be in the wrong browser, or Bridle is missing, turned off or not allowed on this site. Check which it is (see [visual feedback](references/visual-feedback.md)) and tell the user the specific reason. Do not guess addresses or start picking elements before the bar is there.
4. **Every new feedback starts with the modified picker click:** hold **Command+Shift** (macOS) or **Ctrl+Shift** (elsewhere) while clicking **Pick any element to add feedback**, release, then pick the element. Only that click opens Bridle's note for assistants; an ordinary click opens the full Add feedback form meant for people.

## Installed during this conversation

If the Bridle skill was installed earlier in this same conversation, your assistant may not have loaded it for this chat. Read the installed `SKILL.md` (and the reference a step needs) before acting on a Bridle request here, and tell the user that new chats load it by themselves.

## First-time setup and discovery

On the first Bridle-related interaction, unless the user has already confirmed setup or supplied a Bridle **Copy AI prompt**, begin with a short getting-started guide and ask them to complete setup at [bridle.io/setup](https://bridle.io/setup). Do this by default when they ask what Bridle can do, ask how to start, or install the skill. Include the guide and next action in the initial response; do not wait for a separate setup question or stop at a vague prerequisite such as “install the extension” or “enable browser access.” Do not provide the Chrome Web Store URL unless the user explicitly asks for the direct store link.

1. Open the [Bridle setup guide](https://bridle.io/setup) and follow its install steps. Pin or open Bridle in the Chrome profile they want the assistant to use. If they ask for Bridle's main website, give [bridle.io](https://bridle.io/). Only reveal a direct Chrome Web Store URL when explicitly requested.
2. Visit [Bridle](https://bridle.io/). Sign up or sign in if they want account-backed features or Bridle asks them to do so. Some basic feedback capture is available without an account, subject to current limits. The user completes sign-up and authentication themselves; never create an account or handle credentials for them.
3. Enable the assistant's browser control for the same Chrome profile and grant access to the site they want to review. The Bridle skill does not install the extension or connect the browser.
4. If they want implementation, open the website's code repository in the coding assistant as well. A client can still capture and review feedback without a code repository.

For a first-time response, keep the guide concise: (a) install Bridle by following [bridle.io/setup](https://bridle.io/setup); (b) enable the assistant's browser access to the same Chrome profile; (c) open the site to review and ask the assistant to capture one precise Bug, Change, Comment, Feature, Task or Spike; (d) save the requested feedback and report its ID before asking about implementation. Mention that the user completes any sign-up themselves and that a code repository is needed only if they want implementation. Ask them to visit the setup page and finish the steps before attempting browser work.

Always include at least two short, copy-ready example prompts in that first-time guide. Use these three by default so the user can see the capture-only, review-only and implementation paths:

- “Open [website] in Chrome and use Bridle to capture a Bug on [element]: [what happened]. Save it and tell me the REQ ID.”
- “Review my latest Bridle feedback for [website]. Summarize the items and suggest next steps; don't change code yet.”
- “Capture [issue] with Bridle, save it and report the REQ ID, then investigate and fix it in this repository. Verify the result on [local or test URL].”

Keep placeholders obvious, and explain that implementation requires the website repository and a local or test site. Do not send setup instructions as feedback or append them to a Bridle record. If the user already used Bridle's **Copy AI prompt**, skip onboarding and continue from the saved feedback and REQ ID.

## Every change goes through Bridle first

Bridle is the record of what the user asked for and what was done, so it is kept for every change, not only when the user says “Bridle”. When the user asks for a change to a website they have open in their Chrome (“show today's date there”, “add the London weather next to it”, “make this button bigger”), by voice or text:

1. **Capture it in Bridle before touching any code.** Pick the element it is about (for something new, the element it goes next to or into: “next to the date” is the date line), choose the type (something new is a **Feature**, something broken a **Bug**, wording or looks a **Change**), write the request in the user's words, save, and say the REQ ID. One feedback per distinct request; capture all of them before implementing any.
2. **Implement it from Bridle's prompt for that feedback.** With the AI connector on, read its folder (the README, then `feedback/<REQ>.w2c`); otherwise press **Copy prompt** (then **Full**) for that feedback and read the clipboard (`pbpaste` on macOS). The prompt is the specification: the page, the element, how to find it in the code, and the request. Use your knowledge of the repository and what you see on the page to find the code and to fill what the prompt does not say, but never set the prompt aside; if it and what you see disagree, say so and follow the user's words.
3. **Verify on the page** (reload without the cache) and report per REQ ID. Check that the result really works as asked: live data comes from where it should (an API call, not a value copied into the code), today's date is today's. End with the completion link from the prompt so the user can mark it completed.
4. A copied Bridle prompt or a connector item is already saved feedback: reuse its REQ ID; never capture it twice.
5. Other problems you notice on the way are not the user's request: list them; capture or fix one only when asked.
6. If capture is blocked (no access to the user's Chrome, no bar, a quota or sign-in gate), say exactly what blocked it and ask whether to change the code without a Bridle record. Never change the code without one silently.
7. Only the user's own words skip capture (“just change the code, no feedback”). Work that is not a change to a page they are looking at (a refactor, tests, a build script) is not captured.

For reading, review, editing, exports, diagnostics, tickets and completion, use the relevant supported Bridle feature. Repository tools remain necessary for implementation and checks. Do not invent Bridle features or call internal extension messages as a substitute for its visible UI.

## Core operating loop

1. **Understand the request**, and apply [every change goes through Bridle first](#every-change-goes-through-bridle-first) whenever it asks for a change to a page. Identify the site/page, target element, operation (add, edit, replay, diagnostics, Bridle ticket, Jira ticket), and desired outcome. Keep “add a new feedback” distinct from “edit the saved feedback.” A spoken phrase such as “Hey Codex” is a host voice-mode wake phrase, not a Bridle command protocol; recognize the user's task from its intent.
2. **Verify the browser.** Do the [first check](#first-the-right-browser-and-bridles-bar): the user's Chrome, the requested page, Bridle's bar showing. Do not rely on a stale tab or remembered positions.
3. **Capture in Bridle's note.** Read [visual feedback](references/visual-feedback.md#capturing-feedback-as-an-assistant) before the first capture. Reveal the bar (**Command+Shift+9** on macOS, **Ctrl+Shift+9** elsewhere), hold **Command+Shift** / **Ctrl+Shift** while clicking **Pick any element to add feedback**, release, and pick the element. A small handwritten note opens next to it: the type (**CHANGE ▾**) and **Save** at the top, the text in the middle, and under it the element the feedback is on, with **↑ Parent**, **↓ Back**, **Repick** and **×**. Correct the target there (rule 2), set the type, write the request and press **Save**. The user's request is the permission to save: never leave a typed draft waiting for consent. For saved items, open the Bridle feedback workspace and identify the exact item before choosing its item-level action.
4. **Check, then save the requested feedback.** Inspect the selected element preview and the feedback text/type yourself. When they match the user's request, save immediately with **Add**, **Save feedback** or **Update**; do not read a draft back for approval or ask whether to save. The user's request to capture, add, report or update feedback authorizes that Bridle write. Ask first only if the target, type or intended outcome is materially ambiguous, or if Bridle presents a real account/quota gate. Translate intent into a concrete instruction using only what the user said and what is visible. Do not invent a defect, expected behavior, severity or acceptance criteria.
5. **Perform requested follow-up operations.** Use the references below for playback, network diagnostics, and ticket workflows. Creating tickets, sharing diagnostic captures, linking Jira issues, deleting, or resolving feedback changes user data or external systems. Do those only when the user explicitly requested that operation; honor the app's destination/project confirmation and never share a capture just because it was recorded.
6. **Verify the result.** Inspect the resulting confirmation, saved item, replay player, capture review, ticket key/link, or destination page. A click alone is not proof. If the result is ambiguous, inspect saved state before retrying to avoid duplicates.
7. **Report briefly.** State what was completed, on which page/item, and what Bridle visibly confirmed. Mention blockers plainly. Do not claim a Jira ticket exists until Jira's created issue or Bridle's linked key confirms it.

## Rules learned from live use

These come from real sessions in which an assistant drove Bridle in the user's Chrome. Each prevents a failure that happened or nearly happened.

1. **Do not use the right-click menu.** Chrome's native context menu (with **Ask Bridle AI**) is outside the page: browser tools cannot see or click it. Use the bar's **Pick any element to add feedback** instead.
2. **Check the target before you save, and correct it in the note.** The line under the text names the element the feedback is on (for example `<h2#title>` “Welcome back”), and the page highlight shows it. If it is something smaller than what the user meant (part of an icon or a drawing, a word inside a link, an inner `span`), press **↑ Parent** until it names the right element; **↓ Back** undoes a step too far. If it is something else altogether, press **Repick** and pick nearer the middle of the element. A wrong pick also shows as text that is not visible on the page (a screen-reader label such as “Homepage” on a logo) or text that does not match what the user named. Never save against a target you doubt; after two failed attempts, tell the user what the line says and ask.
3. **Gates are the user's step.** If Bridle shows **Sign up to continue**, **Subscribe to continue** or **Share limit reached**, stop. Do not press the account, plan or payment button, and do not sign in. Tell the user the gate, keep their request so it can be repeated, and continue only after they say it is handled. **Maybe later** or × only closes the dialog; the feedback was not saved. Anonymous installs can save only a few feedbacks a day, so a batch may stop part-way: report which items were saved.
4. **Keep the user's words and save without a second approval.** If the user says “just say X”, save exactly X. Otherwise turn clear shorthand into a concise request from what was said and what is on screen (“call this Profile” on the label “For you” → “Change ‘For you’ to ‘Profile’”). Do not read back the draft or ask whether to save; save it and report what Bridle confirmed. Ask a brief question only when the target or requested outcome is materially ambiguous. Never invent replacement text, cause, severity or acceptance criteria.
5. **Choose the type on purpose.** The dialog defaults to **Change**. Pick **Bug**, **Comment**, **Feature**, **Task** or **Spike** when the words say so, and report which type you used. Use Comment for questions, observations and general feedback; do not infer a code-change request from a Comment alone. Change, Bug and Comment note text is red; other note colors follow their type. Completed notes are green.
6. **Names from dictation.** Dictation mishears names; Bridle's own name is covered [above](#the-name-bridle-however-it-was-dictated). When a dictated name or phrase is meant to match text on the page and does not (for example a misspelt person's name in a headline), use the page's text and say so.
   - **Spoken addresses.** “forward slash” is `/`, “hyphen” or “dash” is `-`, “dot” is `.`; a trailing “website”, “page” or “site” usually describes the address, it is not part of it (“example dot com forward slash pricing hyphen plans page” is `example.com/pricing-plans`). If the address you built does not exist, find the page before asking: look at the site's navigation or its `/sitemap.xml` for the closest match, then open it or offer the one or two candidates you found. Ask for the address only when nothing on the site matches.
7. **Read the receipt.** After Cmd/Ctrl+Enter in assistant capture, a dark toast at the bottom of the page reads **Saved REQ-… · Type: text** for a few seconds, and the draft becomes a saved note and marker. If you missed it, find the feedback in the Feedbacks list before retrying. In normal mode, after **Add**, the “What's next?” panel shows **Feedback saved** with the feedback ID (REQ-…) and its text. Report the ID, type and text. Never guess an ID or risk a duplicate save.
8. **IDs are per install, across all sites.** “The latest feedback” means the newest on the page or site the user means, not the highest number overall.
9. **Reveal the bar first.** Always send the platform reveal shortcut before looking for the bar. If absent, follow the recovery sequence in the visual reference, including checking shortcut assignment, profile/site access and restricted pages. Do not report only “bar not found” or silently fall back to normal capture.
10. **Destructive actions need the user's own words.** Delete, remove, reset and turn-off actions only when the user named that action for those items. Deleting a feedback is permanent (there is no recently-deleted list), so stop at the delete confirmation and let the user press it; hiding a marker is reversible and you may do it on request.
11. **Screenshots need the tab in front.** Chrome lets Bridle capture only the visible tab of a window. If the tab you work in is behind another tab, the receipt reads **Feedback saved · screenshot pending**: Bridle takes the screenshot when that tab is shown with the element on screen. Tell the user when this happens. A PDF exported meanwhile says “Screenshot unavailable”.
12. **Check a fix on a fresh page.** After changing a site's files, reload without the cache before judging the result; a normal reload can show the old page.
13. **Leave Bridle's own questions to the user.** “How did that go?” and “Debugging something tricky?” ask about the user's experience or store a preference; do not answer them. If one covers what you need, say so.
14. **Close what you opened.** Close the tabs you created when finished, unless the user wants them.
15. **Several matches: count them, ask once.** When the user names something plural (“the install buttons”, “these links”), or more than one element on the page fits the description, find all of them first. Say how many there are and where (“three install buttons: in the hero, in the install card, at the bottom”), then ask one question: one feedback on each (separate REQ IDs), or one feedback covering all of them (multi-element, see [visual feedback](references/visual-feedback.md#one-feedback-on-several-elements)). If the user already said which, do it without asking. Never pick one of several silently.
16. **There is no page-level feedback.** Every Bridle feedback is attached to an element. For “feedback on the whole page” or “not on any particular element”, attach it to the page's main heading (the `<main>` region when there is no clear heading), begin the text with “Across this page:”, and tell the user which element it is attached to. Do not call it page-level.
17. **Report once.** After saving, give each feedback one line: REQ ID, type, its element in a few words, and the text Bridle confirmed. Do not repeat the same result as a separate “complete” summary.

## Preferred voice interaction

Interpret requests such as “Ask Bridle to open this page, find the hero heading, and add a change request to rename it…” as: navigate/verify the requested site; use Bridle's element picker; verify the exact heading; write the requested change as an explicit command; save it immediately and report the receipt. Do not pause for approval after drafting. Ask one concise question only when page, target, operation, destination, or requested outcome is materially ambiguous (several matching elements is the usual case: rule 15).

Spoken requests contain fillers, restarts and corrections (“uh”, “no, actually don't do that”, “I want, I want to add…”). Act on the last thing the user settled on, and keep their wording for the feedback text only where they said “say exactly…”.

The Bridle UI and its internal extension message names can change. Use the visible labels and current state first; consult implementation-specific notes in the references only as guidance. Do not call undocumented internal extension messages as if they were a supported third-party API.
